## 保持原版玩法的标准

默认保持单位数值、武器克制、射程、速度、生产与装填时间、经济关系、科技前置、视野和操作规则。提高显示帧率不能加快模拟，解码和绘制速度不能改变命令生效时刻。

优先建立以下小场景对照：

1. 移动：地形速度、转向、停靠、占格、步兵子格、碰撞与动态阻挡。
2. 战斗：射程边界、炮塔转向、弹道、伤害/装甲、连发与装填、目标切换和摧毁事件。
3. 经济：价格、建造时间、工厂加成、电力、建造范围、矿车寻矿和卸矿周期。
4. 特殊行为：运输、维修、驻军、隐形/伪装、经验、海空单位、超武和 AI。

每项标记为“规则中明确”“已观察验证”“待确认”或“已实现并回归”。涉及玩法的原版缺陷是否修复，需要作为明确的兼容选项或单独决策；不借底层优化默默更改数值和判定。

玩法兼容与原版二进制存档、原版客户端联机互通分别评估。新引擎的可重放命令和版本化状态保存先服务自身验收，不预先承诺能读取原版存档或加入原版联机。

## 多核与其他性能升级

先建立固定模拟步、稳定实体标识、命令队列、随机数约定和状态摘要。渲染读取稳定状态；工作任务读取快照并返回结果，模拟拥有者在规定步骤按稳定顺序提交。

| 模块 | 并行方式 | 需要维持的边界 |
|---|---|---|
| 资源读取、解压和图像准备 | 后台任务、缓存、预加载 | 资源加载完成的快慢不决定玩法结果 |
| 音视频解码 | 独立缓冲队列 | 不在实时音频回调中读盘、等待或大量分配内存 |
| 寻路与空间查询 | 按请求/批次计算 | 固定提交时刻、稳定的平局选择与失效判断 |
| 视野、候选目标等批量计算 | 读取同一快照并合并结果 | 不并发修改同一个对象，不按线程完成顺序改变判定 |
| 游戏状态变化 | 先保留有序提交 | 伤害、资金、生产完成、创建/销毁与随机调用的顺序可验证 |
| 绘制 | 独立视口、批次、GPU 路径 | 与模拟步解耦，显示帧率独立调整 |

并行寻路不能因为机器较快就提前一帧采用结果；任务预算按确定的工作量定义，兼容模式使用固定的提交规则。随机数不能因线程调度改变消费顺序；更换随机算法或拆分随机流需要单独验证行为差异。

模块形成可重复参考后即可逐步并行化，不必等整个游戏完成。先比较单线程参考与不同工作线程数的逐步状态摘要，再在同一地图、单位、命令序列和速度设置下比较模拟耗时、卡顿、内存及加载时间。不预先承诺随核心数线性加速，也不以 CPU 占用率作为性能通过标准。

其他升级包括 Windows x64 内存与文件处理、连续数据布局、空间索引、缓存、现代 GPU 绘制、宽屏/高 DPI 和可调整显示帧率。扩大单位上限、修改寻路规则等可能影响玩法，应与默认原版配置区分。

## 音乐与过场动画

保留原始资源；通过逻辑资源标识和明确的覆盖映射选择原文件或新增文件。升级编码并不会自动增加原始画面或录音中不存在的细节。

本地对原版 `THEME.MIX` 的三个成员进行头部抽检，均为 RIFF/WAVE、格式标记 `0x0011`、双声道、22,050 Hz。音频阶段需要覆盖 IMA ADPCM，不能只支持未压缩 WAV；这次抽检不表示已经实现音频解码或播放。

| 用途 | 建议首批范围 | 验收重点 |
|---|---|---|
| 原版音效/语音/音乐 | 实际原资源的 WAV/ADPCM 及需要的音频索引容器 | 波形、时长、音量、触发时刻和并发播放 |
| 新音乐 | WAV、FLAC、Ogg Vorbis/Opus；MP3 按需加入 | 流式读取、无缝循环、切歌、暂停与恢复 |
| 原版过场 | BIK/Bink 兼容路径，具体样本再验证 | 音画同步、跳过、结束与任务流程 |
| 新过场 | AV1、HEVC 两个高画质候选；容器与音轨在播放阶段确定 | 同画质体积、软件/硬件解码耗时、设备覆盖、同步、跳过与错误恢复 |

媒体模块继续使用 C 接口，优先评估成熟的 C 解码库，例如 FFmpeg 的 libavformat/libavcodec/libswresample。选型时固定版本和构建范围，检查实际依赖；不需要为了播放功能自行重写复杂视频编解码器。这里是建议范围，不是当前产品已经支持的格式清单。[FFmpeg 官方格式与编解码支持表](https://ffmpeg.org/general.html)

按 2026-10-19 的决定，不将 VP9 纳入本项目首批候选。AV1 与 HEVC 最终使用哪一个，要用同一高质量母版、分辨率、帧率与色深进行编码比较，同时记录主观画质、体积、解码耗时、峰值内存、硬件解码覆盖与音画同步。编码工具可以独立于游戏播放器；播放器继续只依赖所需的 C 解码接口。当前没有执行编码对比，也没有预先选定胜者。

FFmpeg 能共享解封装、解码、转换与播放流程，减少重复实现；具体构建仍需启用对应解码器和必要的外部依赖。例如 AV1 的 libdav1d 需要构建配置，硬件解码还受设备和流参数影响。因此接入工作量接近，但不能把所有格式与硬件组合视为自动通过。[FFmpeg 解码器文档](https://ffmpeg.org/ffmpeg-codecs.html)

原版 `MOVIES01.MIX` 的已知摘要问题继续保留；严格读取器不绕过校验、不修补原件。视频阶段从通过完整性检查的样本验证解码与播放。

## 阵营扩展位置

区分“阵营”和“国家”。阵营、国家、科技树、生产权限、美术、语音和 UI 使用数据定义及稳定标识，避免把“第三阵营”和某个固定数值绑定。

为未来中国保留定义命名空间与扩展接口，默认不激活，不填入未定稿的单位、数值或特殊机制。原版主线应能在只有原版资料的条件下构建、运行和验收；中国设计定稿后，再作为独立内容包接入并验证。

## 接下来的顺序

1. 第六阶段已实现原版最小战场、固定模拟步、回放和状态摘要；下一步对照原版运动学、转向与停靠。
2. 实现原版战斗与基础音效，再接建造、生产、采矿、电力、科技和胜负条件，形成最小遭遇战闭环。
3. 对已有参考测试的资源、寻路和批量查询逐个加入工作任务；保留单线程对照，穿插性能测量。
4. 接入统一音频、视频和现代绘制后端，扩展媒体格式及显示选项；与核心玩法模块分别验收。
5. 补齐原版各类单位、特殊机制、AI、存档、任务与战役；联机协议及同步独立安排。
6. 中国设计完成后，启用预留内容位置，进行阵营玩法和平衡开发。

当前资源基础已足够支持第 1 项，不需要先完成中国设计，也不需要先穷尽所有音视频编码格式。
